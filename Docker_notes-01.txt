What is a container?
Container is a process isolation of an server, a server has a host operating system and on top of server we install docker a software which isolates the os process into separate machines called containers. To run a container, it requires only one thing which is called “os user space” which consists of,
1. System Libraries: Files like libc.so (the glue between your code and the kernel).
2. Package Managers: Tools like apt, yum, or apk used to install more software.
3. Shells & Utilities: Basic commands like ls, cd, grep, and bash.
4. Application Runtime: The specific engine needed to run your code (like the python interpreter or node binary).
5. Config Files: Settings in /etc that tell the system how to behave (like timezones or DNS settings).
Unlike a VM, Container uses HOST OS(KERNEL) to perform specific operations which helps in reduce the additional dependencies requirement and usage of kernel image.

What is an image?
An image is a set of instructions and operations specified to perform along with its dependencies and libs.
we create image using an file(docker file) including all the instructions in that file; each line in a docker file is created like an layer when forming an image. That why we say Images are layers.
Example: Let’s take an ubuntu image, When you pull the ubuntu image from a registry, you aren't getting a bootable OS(Bootloader, Kernel, Init system...); you are getting a root filesystem (the User Space).
What's inside the Ubuntu Image? 
Think of the image as a compressed folder. When it’s uncompressed into a container, it looks like this:
•	The Directory Structure: You'll see the standard Linux folders like /bin, /etc, /var, and /usr.
•	Essential Binaries: It includes tools to move around and manage the system, like ls, cp, mkdir, and bash.
•	The Package Manager: It includes apt, which allows you to download more software (like Python or Nginx) once the container is running.
•	System Libraries: Crucial files like libc.so that allow programs to talk to the host kernel.
•	Metadata: A small JSON file that tells Docker things like "the default user is root" or "the default command to run is /bin/bash."
Note: Every .iso images(.iso is an extension for images) will have an kernel image inside it. Which is called full/complete image. when we use these full images as base image in our docker file the container unpacking this layers in image will also unpacks the kernel image but not be used, cause container is a process running by host/server kernel; a kernel running the process will not initiate another kernel.

Does every image and runtime have a User Space?
Yes, all Images and runtime images will have an user space except bare/scratch images
•  Standard Images (Ubuntu, Python, etc.): These always have a User Space. They provide a familiar environment so you can run commands and install things easily.
•  Minimal Images (Alpine): These have a very tiny User Space (around 5MB). They include only the bare essentials to keep things lightweight.
•  The Exception - scratch: There is a special "empty" image in Docker called scratch. It contains zero files. No shell, no libraries, nothing.
How does it work? You can only use scratch if you have a statically compiled binary (like a Go or C++ app) that has all its libraries built into the single executable file. In this case, your app is the entire User Space.

why can’t containers run windows runtimes on linux host?
Because containers share the host's kernel, they must "speak its language." This creates a compatibility wall that defines what you can and cannot run.
The Kernel Language Barrier 
A container image only contains the User Space (libraries and tools). It does not have its own kernel.
•	Linux Containers are designed to send Linux System Calls (like fork(), mount(), or open()) to a Linux kernel.
•	Windows Runtimes (and .exe files) are designed to send Windows System Calls (like NtCreateProcess or NtOpenFile) to a Windows kernel.
If you put a Windows runtime inside a container and try to run it on a Linux host, the runtime will try to shout "Windows instructions" at the Linux kernel. The Linux kernel simply won't understand them. It’s like trying to run a PlayStation disc in a Nintendo console—the "engine" underneath is built for a different set of instructions.

"Wait, but I've run Linux containers on Windows!" 🤨
You might have noticed that Docker Desktop on Windows can run Linux containers. It feels like magic, but it's actually a clever trick:
1.	The Secret VM: Behind the scenes, Docker Desktop spins up a tiny, lightweight Linux Virtual Machine (often using WSL 2).
2.	The True Host: The Linux containers are actually running on top of that Linux VM's kernel, not the Windows kernel directly.
3.	The Illusion: Docker just makes it look like they are running on Windows.
Why doesn't Linux do the same for Windows? 🐧
While it’s technically possible to run a Windows VM inside Linux to host Windows containers, it is rarely done because:
•	Licensing: Windows requires a paid license to run, even in a container. Linux is free. 💸
•	Weight: Windows "User Space" images are massive (often 1GB–5GB+), while Linux images can be as small as 5MB.
•	Complexity: The Windows kernel and User Space are very tightly coupled, making it much harder to "strip down" for a lightweight container experience compared to Linux.

What is wsl 2 (winows sub system for linux 2)?
Linux containers can’t run on windows machines without an Linux kernel, WSL 2 (Windows Subsystem for Linux 2) is the bridge Microsoft built to solve that exact problem.
Note: wsl 2 is also a light weight vm by Microsoft. We can install it via powershell using command wsl –install
Refrence: https://youtu.be/_fntjriRe48?si=WdsL0Nuk0bdetk7v
The "Hidden" Kernel 🐧
Containers need a Linux kernel to understand their instructions. WSL 2 provides this by running a real Linux kernel inside a highly optimized, lightweight Virtual Machine (VM).
Unlike a traditional VM that takes a long time to "boot up" and hogs resources, the WSL 2 VM:
•	Starts in seconds: It feels almost like running a native Windows app.
•	Shares resources: It only takes the RAM and CPU it needs, and can give it back to Windows when you're finished. 📉
WSL 1 vs. WSL 2: The Big Shift
Before WSL 2, there was WSL 1. It worked very differently:
•	WSL 1: Acted as a "translator." It took Linux system calls and tried to translate them into Windows system calls. This was slow and many complex apps (like Docker!) simply didn't work because the translation wasn't perfect.
•	WSL 2: Stopped translating and just gave the apps a real Linux engine (the kernel) to talk to. This achieved 100% system call compatibility, which is why you can now run Docker Desktop natively on Windows. ✅
